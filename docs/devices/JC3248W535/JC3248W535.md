# JC3248W535 (Shenzhen Jingcai Intelligent)

3.5" ESP32-S3 IPS touch display module. Datasheet in this folder:
`JC3248W535 Specifications-EN.pdf` (SKU `JC3248W535C_I_Y`).

## Specs

| Item | Value |
|---|---|
| Module | ESP32-S3-WROOM-1, dual-core @ 240 MHz, 512 KB SRAM, 384 KB ROM |
| Flash / PSRAM | 16 MB flash / 8 MB PSRAM (datasheet) |
| Radio | Wi-Fi + Bluetooth (integrated in the module) |
| USB | USB-C (one-click download; no separate UART bridge needed) |
| Panel | 3.5" TFT, IPS, 320x480, 16-bit RGB (65K colors) |
| Effective display area | 73.4 x 49.0 mm |
| Module size | 94.5 x 62.0 mm |

| Temperature range | -20 .. +70 degC (storage -30 .. +80 degC) |

| Camera | none |
| Audio | NS4168 I2S amplifier with a speaker connector (not in the datasheet, see "Audio") |
| Storage | TF (microSD) card slot reserved on the module |

| PlatformIO env | `jc3248w535_debug` (`board = esp32-s3-devkitc-1`) |

## Touch

| Item | Value |
|---|---|
| Controller | AXS15231B (same chip as the display controller) |
| Bus / address | I2C, 0x3B |
| SDA | 4 |
| SCL | 8 |
| INT | 3 |
| RST | not documented |
| Fingers | 2, apart down to about 7 mm (measured 2026-10-11) |

The answer to the read command (`b5 ab a5 5a 00 00 00 <length> 00 00 00`) is a header (gesture,
count of fingers) and 6 bytes per finger: x high nibble with the event in bits 6-7, x low, y high
nibble with the finger's id in bits 4-7, y low, and two bytes that count up by one. Espressif's
driver asks for one finger and drops a touch of two; the board file asks for two
(`read_touch`). Measured 2026-10-11: after a lift the header is anything else (0x30 throughout,
taken for no finger, as the driver does); about one answer in 40 during a touch has a good header
but records shifted by a few bytes (no record whose last two bytes count up by one), dropped as a
misread. The driver took those for touches at a wrong place.

Report rate (measured 2026-10-17, `touch log`): the controller makes a new report about every 17
to 22 ms, and a read without a new one answers "no finger". Read every 10 ms a held finger went
`11.11.1.11` (`.` no finger), each gap a lift and a new tap for LVGL. Read every 20 ms
(`Info::touch_sample_ms`) a touch still gets a single such answer now and then (7 in 3 minutes of
use with sliders), never two in a row during a hold or a drag; `read_touch` takes a single one for
a misread, so a lift counts from the second. Taps with a lift shorter than 40 ms can merge.

Ignore the sources that claim touch SDA 15 / SCL 16 / INT 41 - that contradicts the
reference implementations above.

## Camera

Not supported - no camera connector or sensor.

## Audio

The datasheet lists none, but the module has an NS4168 I2S class D amplifier with a speaker
connector. Pins from two independent configurations of the module (the ESPHome example in
[this Home Assistant community thread](https://community.home-assistant.io/t/guition-3-5-320x480-jc3248w535en-lcd-dev-board-working-example/774022)
and an `AUDIO_I2S_*` board config of another project):

| Signal | GPIO |
|---|---|
| BCLK | 42 |
| LRCLK (WS) | 2 |
| DIN of the amplifier (DOUT of the chip) | 41 |

No MCLK, no enable pin (the amplifier's CTRL pin is wired on the board; the firmware writes the
mono samples to both slots, so the selected channel does not matter).

## Storage / other

- TF card (microSD) slot, wired for SPI (schematic sheet 1, "SD_Car"): CS GPIO 10 (CD/DAT3),
  MOSI 11 (CMD), CLK 12, MISO 13 (DAT0), 10k pullups (RN1, DAT2 R15), 3.3 V rail, no card detect.
  The firmware runs it as SDMMC 1 bit with DAT3 held high (docs/architecture.md section 9.3).
- Up to 12 free IOs.
- Li-battery charging circuit.

## Build notes

- PlatformIO: `board = esp32-s3-devkitc-1` with 16 MB flash + 8 MB PSRAM, see
  `sdkconfig.jc3248w535` (OPI/octal PSRAM).
- GUI: LVGL via `lib_deps` (env uses LVGL 9.x; switch to `${lvgl8...}` for 8.x).
  A full-screen canvas/framebuffer is required because the panel has no RAM of its own.
- Display/touch driver stack: AXS15231B QSPI panel driver + AXS15231B I2C touch driver.
- ESPHome equivalent that is known to work: `display: platform: mipi_spi, model: JC3248W535`.

## This project (esp32-hassctrl)

Board `jc3248w535`: `boards/jc3248w535/sdkconfig.defaults`,
`components/board/boards/jc3248w535/jc3248w535.cpp`. Brought up on COM10 on 2026-10-08.

| Item | Verified |
|---|---|
| Chip | ESP32-S3 (QFN56) rev v0.2, PSRAM in the chip: 8 MB octal (AP, generation 3), 80 MHz |
| Flash | 16 MB, manufacturer 0x68 / device 0x4018: Boya (`CONFIG_SPI_FLASH_SUPPORT_BOYA_CHIP`), QIO |
| USB | USB-Serial/JTAG of the chip, no USB-UART bridge: console and log on it (`CONFIG_ESP_CONSOLE_USB_SERIAL_JTAG`) |
| Panel | `esp_lcd_axs15231b` 2.1.1 with the init table of Arduino_GFX 1.6.0, QSPI 40 MHz, SPI mode 0, software reset, no `esp_lcd_panel_disp_on_off()` |
| Touch | answers at 0x3B on SDA 4 / SCL 8, polled every 20 ms (INT on GPIO 3 unused, see below) |
| Backlight | GPIO 1, LEDC 25 kHz, minimum duty 3 of 1023 (2026-10-08) |
| Power | "power on" resets at random (2026-10-09) were the USB cable: gone with a new one. See docs/adding-a-board.md, "Power" |
| SD card | SDMMC 1 bit, CLK 12 / CMD 11 / D0 13, D3 10 held high: a 512 MB card mounted at 40 MHz (2026-10-25) |
| Audio | I2S0 standard mode, 16 bit mono in both slots, 16 kHz, BCLK 42 / WS 2 / DOUT 41 (2026-10-09: clear sound, no pop at start or stop, checked by the user); MP3 files at their own rate (22.05 kHz for the alarm sounds) |

The AXS15231B takes no row address over QSPI (the driver sends no RASET): a write with RAMWR
starts at the first row, RAMWRC continues where the last write ended. Only whole frames, sent from
the top, are drawn correctly, so the board sets `Info::full_frames` and the firmware uses
`components/frame_display` (LVGL direct mode into a PSRAM frame, sent in 32-line bands, rotated in
software). A row range (RASET, as Arduino_GFX sends it) is ignored, and MADCTL MV (hardware
rotation) gave an empty screen. DMA straight from PSRAM failed with "DMA TX underflow" while LVGL
rendered. Clock: 40 MHz; 80 MHz garbled the picture although the datasheet allows 11 ns
(section 5.4.4), 60 MHz is 40 MHz on the ESP32-S3.

Bring-up of the panel (2026-10-08, watched on a camera). Each of these left the screen black:

- the driver's default init table: it is for another panel and ends with "all pixels off" (22h);
- `esp_lcd_panel_disp_on_off(true)` after any init: the driver sends DISPON (29h) without a
  parameter. The table of Arduino_GFX already ends with 29h and a zero byte, which works.

The working settings are those of the vendor-independent demo
[F1ATB/JC3248W535-Demo](https://github.com/F1ATB/JC3248W535-Demo) (Arduino_GFX 1.6.0:
`axs15231b_init_operations`, 32 MHz, SPI mode 0). GPIO 12 (the demo's "touch reset") is not needed
for the panel.

Checked by the user (2026-10-08, docs/adding-a-board.md steps 4 to 6): colors correct (RGB, no
inversion), base orientation portrait 320x480, software rotation in all four orientations with
touch under the finger, no tearing, minimum backlight duty 3.

Touch INT on GPIO 3 (measured 2026-10-17, edges timestamped against the reads, 18 touches): high
while idle, a low pulse of 1-2 ms with every report, every 16-17 ms (14-19); no pulse at a lift,
the pulses just stop. During a hold the controller skips a report now and then (gaps of 34-36 ms,
once 49 ms); a read in such a gap, or at the moment of a pulse, answers "no finger", which is the
misread that `read_touch` drops. INT is not used: a lift still needs a timeout over the longest
gap (50 ms or more), longer than the 20-40 ms of polling, so fast taps would merge sooner.

## Deep sleep

Tried 2026-10-11 for a battery remote, cancelled. On this board a deep sleep still takes **30 to
40 mA** (measured by the user over USB): the ESP32-S3 sleeps, but the rest of the board does not.
With the CPU held in the ROM (BOOT held) the board took 18 mA, with RST held 110 mA (the backlight
line floats and the backlight comes on). The battery circuit is a plain IP5306 without I2C, the
touch INT (GPIO 3) reports touches only while the panel is on, and a running panel costs about
50 mA. Not usable for a battery device; no deep sleep in the firmware.
